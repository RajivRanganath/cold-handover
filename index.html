LedgerGuard, and the decisions behind it

A self verifying AI finance controller that reconciles payment settlements. It checks that the money from every payment actually arrived, and refuses to close anything it cannot prove.

LLM reasoning is not financial truth. Financial truth is deterministic accounting state plus verified evidence. The AI may propose, the financial system must prove.

  • An independent Shadow Ledger computes what the money should have been, and never reads the provider's settlement or bank records to decide that.

    Source: README, What it does (1)

  • All money is integer paise; no float ever touches it.

    Source: README, What it does (1)

  • Deterministic code handles everything it can prove; the AI only sees cases that could not be proved.

    Source: README, What it does (2-3)

  • An Evidence Gate re-proves every AI claim against the records before anything is closed.

    Source: README, What it does (4)

  • When proof is insufficient it abstains; abstention is a designed outcome, not a failure.

    Source: README, What it does (5)

  • No model-generated confidence number; a named Verification Score ("5 of 7 evidence checks passed") instead.

    Source: README, Why this is not just an LLM reconciliation bot

Putting my own handover to the test

Four tasks, each fixed before its attempts ran (three in round 1, one harder task in round 2); five fresh attempts each (20 total), in an order fixed before running; each checked afterwards by hidden tests and comparisons the agent could not see.

  1. Tasks fixed in advance
  2. A fresh, sandboxed agent each time, with nobody to ask
  3. Five attempts per task
  4. Hidden checks it could not see

Each attempt: fresh copy of the repository, empty configuration (no memory, instructions or history), web tools disabled, sandbox limited to its own folder, nobody available to answer questions. Agent: Claude Code 2.1.316, model claude-haiku-5-5.

Decisions I made along the way

  • Tested a pinned historical snapshot (5 Sep 2026) rather than the latest code.

  • Every attempt started cold: fresh copy, empty config, no memory, sandboxed, hidden checks.

  • Used a small, efficient model (Claude Haiku 5.5) rather than a frontier model.

  • Fixed the tasks and checks before any measured attempt, and kept one task held out.

  • When both pilots passed without needing an explanation, ran a baseline audit instead of writing an extra handover just to show an improvement.

What this does and does not show

This is a small experiment with one repository and one agent configuration. It measures agent task completion, not human onboarding.

The agent had the whole repository: README, docs and code. The audit does not separate the README's contribution from the code's.

It cannot claim

  • that the README alone caused the success: the agent also had the code and the other docs
  • that the result generalises to other tasks, agents, models or repositories
  • statistical significance (five attempts per task is a small descriptive sample)
  • any benefit for human newcomers
  • that the documentation has no gaps; harder or vaguer tasks might expose some
  • that the model had never seen this public repository in training
  • anything new about LedgerGuard's own live-model benchmark numbers

Disclosures

  • The agent's shell could reach services on the Mac's localhost (the project's tests need local sockets). One attempt (M-T1-05) checked port 20128; nothing was listening.
  • Outbound internet was not blocked at network level; web search and fetch tools were disabled, and no attempt used the internet beyond the model API.
  • The login token was visible to the agent's shell; every output was scanned for it after every attempt and it never appeared.
  • Two exploratory pilots ran before the protocol was frozen and are excluded from the counts.
  • Round 2 (T4) was designed after round 1's results were known, to test a harder, vaguer task. It ran on Claude Code 2.1.325 instead of 2.1.316 (the older version was no longer installed); the newer version loads its built-in plugins. Model, snapshot and sandbox were the same.
  • For T4, one check (a fee overcharge combined with an unexplained shortfall) was moved from pass/fail to an unscored depth measure before any attempt ran, because the bug report does not mention it. All five attempts handled it anyway.
  • T4 had two pilots, both excluded: the first never started (the harness pointed at an uninstalled Claude Code version) and the second passed.
